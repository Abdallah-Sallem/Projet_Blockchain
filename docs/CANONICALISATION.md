# Empreintes et signatures

Le format binaire v1 commence par les octets ASCII `FedTrace`, zéro, `v1`. Chaque champ variable est précédé d'une longueur uint64 little endian. Le domaine `model` ou `update` est un champ distinct ; un même tableau n'a donc pas la même empreinte selon son rôle. Les contributions ancrent des **deltas poids locaux moins poids parents**, pas les poids complets.

Après le domaine vient le nombre de paramètres uint64 little endian. Pour chaque nom trié selon l'ordre Unicode Python : nom UTF-8 préfixé par longueur ; dtype NumPy explicite little endian préfixé par longueur ; nombre de dimensions uint64 ; chaque dimension uint64 ; octets contigus en ordre C préfixés par longueur. Dtypes acceptés : entiers signés/non signés et flottants de 1, 2, 4 ou 8 octets lorsque NumPy les représente. NaN et infinis sont refusés. Booléens, objets et chaînes sont refusés. Les flottants signés zéro conservent leur représentation binaire ; aucune normalisation numérique ou tolérance n'est appliquée.

Les poids sont sauvegardés en NPZ, chargés avec `allow_pickle=False` puis hachés dans ce format. Les octets ZIP/NPZ ne sont jamais l'identité canonique du modèle. SHA-256 fournit 32 octets, présentés en 64 chiffres hexadécimaux.

Les métadonnées et explications utilisent JSON UTF-8 : clés triées, séparateurs `,` et `:`, sans espaces, Unicode non échappé, nombres non finis refusés. Ce format est défini pour ce programme Python et ne prétend pas implémenter RFC 8785. Un autre langage doit reproduire les représentations numériques Python, ou vérifier directement les octets d'origine. L'empreinte de l'explication porte sur **les octets exacts du fichier remis dans la réponse** : le champ `explanation_artifact` livre leur chaîne UTF-8 et `/api/decisions/{id}/explanation` les livre directement en pièce jointe. Une modification même sémantiquement neutre du fichier est détectée. L'explication est une somme de contributions `x_i × w_i` au logit, avec biais et version de modèle ; ce n'est pas une causalité médicale ni un SHAP générique.

Les enveloppes sont signées avec secp256k1 : signature Ethereum personal-sign du SHA-256 (32 octets) des métadonnées canoniques. Le registre récupère l'adresse et la compare au registre local d'identités. Le contrat réalise la récupération sur ces mêmes octets. La non-répudiation est limitée à la possession des clés locales, sans PKI hospitalière, horodatage externe, rotation ni révocation clinique. Les clés privées ne sont pas incluses dans les enregistrements.
